# Forward-compatible enums and tagged unions

## 1. Question and scope

When a server adds an enum value or a tagged-union variant, how do typed clients represent the value they don't recognise, what do they keep, and how do they stop generic code from ignoring it? This research informs Telegramium, the Scala Telegram Bot API library generated by iozhik. The options on the table are:

- **(a)** a wrapper, `sealed trait OpenEnum[+T]` with `Known(value: T)` and `Unknown(value: String, raw: Json)`, for tagged-object families such as MessageEntity, ChatMember and RichText, where `raw` lets an unknown nested value be sent back exactly as received (issue #723);
- **(b)** an extra case inside each enum;
- typing string enums such as `Chat.type` as `OpenEnum[ChatType]`, and deciding what their `Unknown` holds.

The document merges four notes researched on 2026-11-12: Scala; Haskell, OCaml and F#; Rust, Swift, Kotlin, Go, TypeScript, Java and C#; and schema languages, API guidelines, the Telegram Bot API and Telegram libraries. Links are pinned to the commits that were read wherever the notes pinned them.

## 2. Summary for the decision

- **The per-enum case is the most common generated shape.** ScalaPB `Unrecognized` ([ProtobufGenerator.scala#L89-L99](https://github.com/scalapb/ScalaPB/blob/560510687078af4e928ba17bd73a1692c1707d1d/compiler-plugin/src/main/scala/scalapb/compiler/ProtobufGenerator.scala#L89-L99)), smithy4s `$Unknown` ([Renderer.scala#L1518-L1531](https://github.com/disneystreaming/smithy4s/blob/07e8cd52a0e53636369bd0bc3045681158c803ce/modules/codegen/src/smithy4s/codegen/internals/Renderer.scala#L1518-L1531)), Caliban `__Unknown` ([ClientWriter.scala#L735-L743](https://github.com/ghostdogpr/caliban/blob/e278c239a34d0df969417f05716c0a9225af5860/codegen/src/main/scala/caliban/codegen/ClientWriter.scala#L735-L743)), swift-protobuf `UNRECOGNIZED(Int)` ([API.md L159-168](https://github.com/apple/swift-protobuf/blob/f66e5e16c19ccc826a9fc75796250a152b54932b/Documentation/API.md#L159-L168)), smithy-rs `Unknown(UnknownVariantValue)` ([ClientEnumGenerator.kt L185-206](https://github.com/smithy-lang/smithy-rs/blob/3e014c27dd4c631a725cc4d9ba1ba29278b6e941/codegen-client/src/main/kotlin/software/amazon/smithy/rust/codegen/client/smithy/generators/ClientEnumGenerator.kt#L185-L206)) and smithy-kotlin `SdkUnknown` ([kotlin-smithy-sdk.md L535-717](https://github.com/smithy-lang/smithy-kotlin/blob/f3f9d5110f540810fb2d7391889f5433ce819cb4/docs/design/kotlin-smithy-sdk.md#L535-L717)) all use it.
- **Several libraries moved toward a split between known and unknown at the type level.**
  - enumeratum's maintainer declined an in-enum `Unknown` as an "exhaustive-pattern-checking tax/burden" and proposed a wrapper, `EnumOrUnknown` ([#392](https://github.com/lloydmeta/enumeratum/issues/392)).
  - Apollo iOS dropped its per-enum `__unknown` case in favour of a generic `GraphQLEnum<T>` in 1.0 ([CodegenProposal.md L472-529](https://github.com/apollographql/apollo-ios/blob/fea2613e7d69dbf532b5aad897722be638f345be/CodegenProposal.md#L472-L529)).
  - ScalaPB added a `Recognized` sub-trait and `asRecognized` ([ProtobufGenerator.scala#L39-L46](https://github.com/scalapb/ScalaPB/blob/560510687078af4e928ba17bd73a1692c1707d1d/compiler-plugin/src/main/scala/scalapb/compiler/ProtobufGenerator.scala#L39-L46)).
  - Apollo Kotlin's newest mode adds a `__Known` sub-interface so that code can "only deal with known enums" ([Service.kt L537-598](https://github.com/apollographql/apollo-kotlin/blob/257ec5f007c3002feb7a76d68fbaa895d2a6e8b6/libraries/apollo-gradle-plugin/src/main/kotlin/com/apollographql/apollo/gradle/api/Service.kt#L537-L598)).
- **The Haskell redesigns concern exhaustiveness, not wrapper versus case.**
  - amazonka replaced closed ADTs with a newtype plus pattern synonyms because "AWS introduces new values to its enums, which causes crashes" ([PR #597](https://github.com/brendanhay/amazonka/pull/597)).
  - proto-lens went the other way, from a newtype back to a sum type, because "the type checker won't tell us" about new cases ([#150](https://github.com/google/proto-lens/issues/150)).
  - With `COMPLETE` pragmas the two designs converge: both force a raw branch while still checking the known cases.
- **Enums and unions are treated asymmetrically almost everywhere.** smithy-rs, smithy-kotlin and AWS Java keep the raw string for enums, but they keep no payload for unknown union members and refuse to serialize them ([UnionGenerator.kt L177-180](https://github.com/smithy-lang/smithy-rs/blob/3e014c27dd4c631a725cc4d9ba1ba29278b6e941/codegen-core/src/main/kotlin/software/amazon/smithy/rust/codegen/core/smithy/generators/UnionGenerator.kt#L177-L180), [SerializeUnionGenerator.kt L74](https://github.com/smithy-lang/smithy-kotlin/blob/f3f9d5110f540810fb2d7391889f5433ce819cb4/codegen/codegen/src/main/kotlin/aws/smithy/kotlin/codegen/rendering/serde/SerializeUnionGenerator.kt#L74)). The Smithy spec itself makes unknown enums a MUST and unknown union variants only a SHOULD ([simple-types#enum](https://smithy.io/2.0/spec/simple-types.html#enum), [aggregate-types#client-error-correction](https://smithy.io/2.0/spec/aggregate-types.html#client-error-correction)).
- **A handful of libraries keep whole unknown payloads.**
  - smithy4s's opt-in `@jsonUnknown` member captures "the entire document at the cursor" and writes it back ([#1585](https://github.com/disneystreaming/smithy4s/issues/1585)).
  - python-telegram-bot keeps unknown keys in `api_kwargs` and re-emits them in `to_dict` ([_telegramobject.py L494-L502](https://github.com/python-telegram-bot/python-telegram-bot/blob/41e3633bd1b4e51693ee57059828a59a9773618a/src/telegram/_telegramobject.py#L494-L502)).
  - Telegram.Bot has `RichTextUnsupported(TypeString, JsonDocument)` ([Extend.Types.cs L292-L300](https://github.com/TelegramBots/Telegram.Bot/blob/9650e477a4838a572e61caf089a73c014f435db2/src/Telegram.Bot/Extend.Types.cs#L292-L300)).
  - teloxide has `UpdateKind::Error(serde_json::Value)`, filled by a re-parsing hack ([net/request.rs L114-153](https://github.com/teloxide/teloxide/blob/3c46b96e0dc0cabc75d6430c4566d7e2e12fd233/crates/teloxide-core/src/net/request.rs#L114-L153)).
  - protobuf keeps unknown oneof members as unknown fields, while the oneof itself reads `NOT_SET` ([proto3#backward](https://protobuf.dev/programming-guides/proto3/#backward)).
- **For a scalar enum, the string or int is the whole wire value.** Every design in these notes that opens a scalar enum stores just that value, and none stores JSON. atdgen's earlier `Unknown of (string * json option)` was removed in 2.0 ([CHANGES L415-420](https://github.com/ahrefs/atd/blob/d465f64c708dfdbef1852f7fe25246bf4692e326/CHANGES.md#L415-L420)).
- **Building `Unknown("X")` by hand breaks equality and forward compatibility.**
  - Code that matches `Unknown(v) if v == "IpV8"` silently stops matching once an SDK upgrade makes "IpV8" a known value ([smithy-rs #627 comment](https://github.com/smithy-lang/smithy-rs/issues/627#issuecomment-995923092)).
  - smithy-rs makes the payload opaque and normalises input through `From<&str>`.
  - Apollo Kotlin 4 made `UNKNOWN__` private ([4.0 migration L642-653](https://github.com/apollographql/apollo-kotlin/blob/257ec5f007c3002feb7a76d68fbaa895d2a6e8b6/docs/source/migration/4.0.mdx#L642-L653)).
  - Apollo iOS keeps construction public but compares on the raw string, so `.unknown("X") == .case(.X)` ([GraphQLEnum.swift L84-141](https://github.com/apollographql/apollo-ios/blob/fea2613e7d69dbf532b5aad897722be638f345be/Sources/ApolloAPI/GraphQLEnum.swift#L84-L141)).
- **Clients are required to be able to send unknown values.** Smithy says clients "MUST provide the capability of sending and receiving unknown enum values" ([#enum](https://smithy.io/2.0/spec/simple-types.html#enum)). Servers may still reject such values: Microsoft says services SHOULD NOT accept them ([Guidelines.md L432-L440](https://github.com/microsoft/api-guidelines/blob/1c58ca7f1eb51768cb4e21facd6ce0154ee4db64/azure/Guidelines.md#L432-L440)), and "Stripe validates request values" ([api/enums](https://docs.stripe.com/api/enums)).
- **Unknown values are kept out of `values` lists everywhere.** Examples are ScalaPB `Seq[Recognized]` ([CHANGELOG.md#L62](https://github.com/scalapb/ScalaPB/blob/560510687078af4e928ba17bd73a1692c1707d1d/CHANGELOG.md#L62)), smithy4s, Caliban, AWS `knownValues()`, swift-protobuf `allCases` and Apollo. amazonka went further and deleted `Bounded`/`Enum`, because `Bounded` "becomes a lie" ([#597](https://github.com/brendanhay/amazonka/pull/597)).
- **Three silent-loss traps recur.**
  - Mapping to a default: prost's getter ([README L213-214](https://github.com/tokio-rs/prost/blob/894f4a7f9c41f1afb8455fb6e521c067815f608d/README.md#L213-L214)), kotlinx `coerceInputValues`, openapi-generator `unknown_default_open_api`, Avro `default`, and Telegram.Bot's unnamed `0`.
  - A fallback that also catches *malformed known* variants: circe `Decoder.or`, and teloxide's `.ok()` arms ([update.rs L430-456](https://github.com/teloxide/teloxide/blob/3c46b96e0dc0cabc75d6430c4566d7e2e12fd233/crates/teloxide-core/src/types/update.rs#L430-L456)).
  - Exceptions that escape the decoder: bot4s throws inside circe's `map` ([ChatType.scala#L13-L14](https://github.com/bot4s/telegram/blob/07e15ea01caa3d09d4c6d93af8efe8ed7b9307ef/core/src/com/bot4s/telegram/models/ChatType.scala#L13-L14)).
- **Telegram guarantees nothing explicitly, and clients that fail closed lose whole updates.** The docs say "Currently, can be …" ([#messageentity](https://core.telegram.org/bots/api#messageentity)), and new entity types arrive in minor releases ([2026-11-09](https://core.telegram.org/bots/api-changelog#november-9-2026)). bot4s, telegram-bot-simple and teloxide all drop the entire update when one nested enum is unknown.

## 3. Comparison table

"Kept" means what survives for an unknown value: nothing, the tag, or the whole payload. For an enum the tag is the whole payload.

| ScalaPB | in-enum case `Unrecognized(Int)` | tag (int); messages keep `UnknownFieldSet` | oneof: only `Empty`, payload kept in unknown fields | yes; conversion to Java fails | sealed; `Recognized` sub-trait; `values: Seq[Recognized]` |
| smithy4s | in-enum `$Unknown(str)`; union opt-in `@jsonUnknown other: Document` | enum: tag; union: whole payload, written back | enum openness lives in the schema; union openness is a JSON/Document-only hint | yes | sealed; `values` known-only; `$unknown` prism |
| circe / zio-json / jsoniter-scala | fail; user writes the fallback | whatever the user keeps | n/a | user code | sealed only |
| Scala 3 `enum` | none built in; user adds a class case | user code | n/a | yes | parameterized cases are excluded from `values` |
| enumeratum | none; maintainer proposed a wrapper | user code | n/a | user code | maintainer rejected the in-enum "tax" |
| Caliban client | opt-in in-enum `__Unknown(value)` | tag | unions/interfaces fail | yes | `values` excludes it |
| zio-aws | in-enum `unknownToSdkVersion` object | nothing (from a reading of the code) | unions not checked | no | sealed |

## 4. Per-ecosystem findings

### 4.1 Scala

**ScalaPB.**
- **Representation.** Each enum gets `final case class Unrecognized(unrecognizedValue: Int)` with `UnrecognizedEnum`, and `fromValue` falls through to it ([ProtobufGenerator.scala#L89-L99](https://github.com/scalapb/ScalaPB/blob/560510687078af4e928ba17bd73a1692c1707d1d/compiler-plugin/src/main/scala/scalapb/compiler/ProtobufGenerator.scala#L89-L99)). A proto value named `UNRECOGNIZED` is rejected at codegen ([ProtoValidation.scala#L44-L49](https://github.com/scalapb/ScalaPB/blob/560510687078af4e928ba17bd73a1692c1707d1d/compiler-plugin/src/main/scala/scalapb/compiler/ProtoValidation.scala#L44-L49)).
- **What is kept.** The enum keeps the int, which is the whole wire value. Messages keep unknown fields in `UnknownFieldSet` ([UnknownFieldSet.scala#L14](https://github.com/scalapb/ScalaPB/blob/560510687078af4e928ba17bd73a1692c1707d1d/scalapb-runtime/src/main/scala/scalapb/UnknownFieldSet.scala#L14)). That became the default in 0.10.0, as a deliberate breaking change: "Once the message is serialized again, the unknown fields will be serialized too" ([CHANGELOG.md#L264-L275](https://github.com/scalapb/ScalaPB/blob/560510687078af4e928ba17bd73a1692c1707d1d/CHANGELOG.md#L264-L275)).
- **Oneofs.** Oneofs have only `Empty` ([ProtobufGenerator.scala#L135](https://github.com/scalapb/ScalaPB/blob/560510687078af4e928ba17bd73a1692c1707d1d/compiler-plugin/src/main/scala/scalapb/compiler/ProtobufGenerator.scala#L135)). An unknown tag goes to `_unknownFields__.parseField` ([ParseFromGenerator.scala#L226-L229](https://github.com/scalapb/ScalaPB/blob/560510687078af4e928ba17bd73a1692c1707d1d/compiler-plugin/src/main/scala/scalapb/compiler/ParseFromGenerator.scala#L226-L229)), so the payload is kept at the message level, not inside the union.
- **Type-level split.** A `sealed trait Recognized` covers every known case, `asRecognized: Option[Recognized]` is generated, and `isUnrecognized` sits on the base trait ([ProtobufGenerator.scala#L39-L46](https://github.com/scalapb/ScalaPB/blob/560510687078af4e928ba17bd73a1692c1707d1d/compiler-plugin/src/main/scala/scalapb/compiler/ProtobufGenerator.scala#L39-L46), [GeneratedMessageCompanion.scala#L27-L43](https://github.com/scalapb/ScalaPB/blob/560510687078af4e928ba17bd73a1692c1707d1d/scalapb-runtime/src/main/scala/scalapb/GeneratedMessageCompanion.scala#L27-L43)). `values` was recently narrowed to `Seq[Recognized]` (#2179, [CHANGELOG.md#L62](https://github.com/scalapb/ScalaPB/blob/560510687078af4e928ba17bd73a1692c1707d1d/CHANGELOG.md#L62)).
- **Construction.** `Unrecognized(n)` is public. Conversion to Java fails with `require(!isUnrecognized, ...)` ([ProtobufGenerator.scala#L108](https://github.com/scalapb/ScalaPB/blob/560510687078af4e928ba17bd73a1692c1707d1d/compiler-plugin/src/main/scala/scalapb/compiler/ProtobufGenerator.scala#L108)).
- **History.** Versions before 0.5.x threw a `MatchError` on unknown values ([generated-code.md#L345-L348](https://github.com/scalapb/ScalaPB/blob/560510687078af4e928ba17bd73a1692c1707d1d/docs/src/main/markdown/generated-code.md#L345-L348)).

**smithy4s.**
- **Enums.** `alloy#openEnum` generates `$Unknown(str: String)` (or `int: Int`) plus `fromStringOrUnknown` ([Renderer.scala#L1518-L1531](https://github.com/disneystreaming/smithy4s/blob/07e8cd52a0e53636369bd0bc3045681158c803ce/modules/codegen/src/smithy4s/codegen/internals/Renderer.scala#L1518-L1531)). The `$` prefix avoids "collisions with actual enum values" ([open-enums doc#L25-L33](https://github.com/disneystreaming/smithy4s/blob/07e8cd52a0e53636369bd0bc3045681158c803ce/modules/docs/resources/markdown/04-codegen/01-customisation/12-open-enums.md#L25-L33)).
- **Schema shape.** In 0.18.x `EnumTag` had four cases, including `OpenStringEnum(unknown: String => E)` ([v0.18.53 EnumTag.scala](https://github.com/disneystreaming/smithy4s/blob/v0.18.53/modules/core/src/smithy4s/schema/EnumTag.scala)). 0.19 reworked it to `StringEnum(value, unknown: Option[String => E])` ([EnumTag.scala#L20-L25](https://github.com/disneystreaming/smithy4s/blob/07e8cd52a0e53636369bd0bc3045681158c803ce/modules/core/src/smithy4s/schema/EnumTag.scala#L20-L25)). Either way, enum openness is part of the schema, so every codec sees it.
- **Unions.** Unions are opt-in open (since 0.18.35, #1677): you add a member such as `@jsonUnknown other: Document` ([unions doc#L170-L189](https://github.com/disneystreaming/smithy4s/blob/07e8cd52a0e53636369bd0bc3045681158c803ce/modules/docs/resources/markdown/04-codegen/02-unions.md#L170-L189)).
  - The member wraps "the **entire document at the cursor**", and serialization "will write the entire document back" ([#1585](https://github.com/disneystreaming/smithy4s/issues/1585)).
  - The encoder omits the tag wrapper for that member ([SchemaVisitorJCodec.scala#L1110-L1120](https://github.com/disneystreaming/smithy4s/blob/07e8cd52a0e53636369bd0bc3045681158c803ce/modules/json/src/smithy4s/json/internals/SchemaVisitorJCodec.scala#L1110-L1120)).
  - A tagged object with several root keys is rejected rather than captured ([#1713](https://github.com/disneystreaming/smithy4s/issues/1713)).
  - Union openness is only a hint on one alternative. `UnionSchema` has no unknown hook ([Schema.scala#L179](https://github.com/disneystreaming/smithy4s/blob/07e8cd52a0e53636369bd0bc3045681158c803ce/modules/core/src/smithy4s/schema/Schema.scala#L179)). The JSON and Document codecs drop hinted alternatives from the tag map and use them as the fallback ([SchemaVisitorJCodec.scala#L1005-L1017](https://github.com/disneystreaming/smithy4s/blob/07e8cd52a0e53636369bd0bc3045681158c803ce/modules/json/src/smithy4s/json/internals/SchemaVisitorJCodec.scala#L1005-L1017)).
  - Other protocols don't support it, and a generic visitor that ignores the hint sees an ordinary member called `other`.
- **Guards.** `values` lists only known cases ([Renderer.scala#L1534-L1543](https://github.com/disneystreaming/smithy4s/blob/07e8cd52a0e53636369bd0bc3045681158c803ce/modules/codegen/src/smithy4s/codegen/internals/Renderer.scala#L1537-L1543)), a `$unknown` prism is generated ([Renderer.scala#L1166](https://github.com/disneystreaming/smithy4s/blob/07e8cd52a0e53636369bd0bc3045681158c803ce/modules/codegen/src/smithy4s/codegen/internals/Renderer.scala#L1166)), and the ADT is sealed. `$Unknown("NEW")` and `OtherCase(Document)` are both constructible.
- **Rationale.** smithy4s departs from Smithy's open-union default because open unions "can only work within the context of a particular protocol", and it wants "strict type safety guarantees - such as the ability to perform exhaustive pattern matches" ([unions doc#L152-L166](https://github.com/disneystreaming/smithy4s/blob/07e8cd52a0e53636369bd0bc3045681158c803ce/modules/docs/resources/markdown/04-codegen/02-unions.md#L152-L166)). Its docs suggest a plain `String` "will better suit" fields whose values aren't known in advance (open-enums doc L6).

**circe.**

### 4.3 Rust, Swift, Kotlin, Go, TypeScript, Java, C#

**Rust `#[non_exhaustive]`.**
- The attribute forces downstream matches to include a wildcard, and it blocks downstream construction of structs and variants ([RFC L12-17](https://github.com/rust-lang/rfcs/blob/master/text/2008-non-exhaustive.md#L12-L17)). The motivating case is `io::ErrorKind` ([RFC Motivation](https://github.com/rust-lang/rfcs/blob/master/text/2008-non-exhaustive.md#motivation)).
- The wildcard loses "missed variant" warnings. A lint for that was left open ([RFC L521-525](https://github.com/rust-lang/rfcs/blob/master/text/2008-non-exhaustive.md#L521-L525)) and is still unstable ([rust#89554](https://github.com/rust-lang/rust/issues/89554)).

**serde.**
- `#[serde(other)]` is unit-only ([serde docs](https://github.com/serde-rs/serde-rs.github.io/blob/c4a897bc01fb358075ddd1f6235ed54081e88b84/_src/variant-attrs.md#L93-L102)), so it keeps neither tag nor payload. - serde has no guard against swallowing unknowns.

- **Construction.** It happens only via `From<&str>`, which maps known strings to known variants ([L42-66](https://github.com/smithy-lang/smithy-rs/blob/3e014c27dd4c631a725cc4d9ba1ba29278b6e941/codegen-client/src/main/kotlin/software/amazon/smithy/rust/codegen/client/smithy/generators/ClientEnumGenerator.kt#L42-L66)). `try_parse` rejects unknowns ([L122-131](https://github.com/smithy-lang/smithy-rs/blob/3e014c27dd4c631a725cc4d9ba1ba29278b6e941/codegen-client/src/main/kotlin/software/amazon/smithy/rust/codegen/client/smithy/generators/ClientEnumGenerator.kt#L122-L131)).

### 4.4 Schema languages and API guidelines

**Protocol Buffers.**
- **Open vs closed.** Open and closed enums differ only in how they treat unknown values ([enum.md#definitions](https://protobuf.dev/programming-guides/enum/#definitions)). An open enum stores the int; a closed enum moves it to unknown fields and reports the default. proto3 and editions default to open ([editions features#enum_type](https://protobuf.dev/editions/features/#enum_type)).
- **Preservation.** Unknown enum values and fields are preserved and re-serialized ([proto3#enum](https://protobuf.dev/programming-guides/proto3/#enum), [proto3#unknowns](https://protobuf.dev/programming-guides/proto3/#unknowns)). JSON serialization loses them ([proto3#retaining](https://protobuf.dev/programming-guides/proto3/#retaining)): ProtoJSON implementations "generally do not propagate unknown fields" ([json](https://protobuf.dev/programming-guides/json/)).
- **Oneofs.** An unknown oneof member reads as `NOT_SET`, which is indistinguishable from "unset", while the payload survives as an unknown field ([proto3#backward](https://protobuf.dev/programming-guides/proto3/#backward)).
- **Java.** `UNRECOGNIZED` plus `getXValue()`; `setXValue(2)` works and `setX(UNRECOGNIZED)` throws ([enum.md#java](https://protobuf.dev/programming-guides/enum/#java)).
- **Regret.** "Proto3 and editions use *open* enums specifically because of the unexpected behavior that *closed* enums cause" ([enum.md#history](https://protobuf.dev/programming-guides/enum/#history)). For example, a closed repeated enum `[0,2,1,2]` reserializes as `[0,1,2,2]` ([enum.md](https://protobuf.dev/programming-guides/enum/)).
- **Conformance.** Support varies by language ([#known-issues](https://protobuf.dev/programming-guides/enum/#known-issues)):
  - C++, Java and Kotlin treat proto3 enums imported into proto2 as closed.
  - C#, Go, JSPB and Ruby treat all enums as open.
  - Dart treats all enums as closed.
  - PHP and Swift conform, as do Python above 4.22.0 and Objective-C above 3.22.0.
  - `legacy_closed_enum` keeps the old behaviour ([features#legacy_closed_enum](https://protobuf.dev/editions/features/#legacy_closed_enum)).

**Smithy.**
- Enums and intEnums are open, and previously generated clients "MUST NOT fail" on unknown values ([simple-types#enum](https://smithy.io/2.0/spec/simple-types.html#enum), [#intenum](https://smithy.io/2.0/spec/simple-types.html#intenum)). Clients "MUST provide the capability of sending and receiving unknown enum values".
- Adding union members is backward-compatible, and clients "SHOULD NOT fail" on them ([evolving-models#updating-unions](https://smithy.io/2.0/guides/evolving-models.html#updating-unions)). Generators "SHOULD define an unknown variant" and avoid member names like `Unknown` ([aggregate-types#client-error-correction](https://smithy.io/2.0/spec/aggregate-types.html#client-error-correction)). New members SHOULD be appended ([#adding-new-union-members](https://smithy.io/2.0/spec/aggregate-types.html#adding-new-union-members)).
- The spec does not require keeping a union's payload. `document` is "protocol-agnostic open content" ([#document](https://smithy.io/2.0/spec/simple-types.html#document)), the natural carrier for one.

**Avro.**
- An unknown symbol is replaced by the reader's `default`, or else "an error is signalled" ([spec#enums](https://avro.apache.org/docs/1.12.0/specification/#enums)). Unmatched union branches error ([#schema-resolution](https://avro.apache.org/docs/1.12.0/specification/#schema-resolution)).
- Avro resolves with both writer and reader schemas present, which is unlike the JSON API case.

**Thrift.**
- The IDL doc is silent on unknowns ([idl](https://thrift.apache.org/docs/idl)). Whether a normative rule exists elsewhere is unconfirmed.
- In the Java generator, unknown enum ints become `null` ([t_java_generator.cc L625-L640](https://github.com/apache/thrift/blob/6050f83e10ae926deccf0c2aa0c0f3e90dbd54cf/compiler/cpp/src/thrift/generate/t_java_generator.cc#L625-L640)). Unknown union fields are skipped ([L1265-L1290](https://github.com/apache/thrift/blob/6050f83e10ae926deccf0c2aa0c0f3e90dbd54cf/compiler/cpp/src/thrift/generate/t_java_generator.cc#L1265-L1290)), which leaves an empty union that throws on write ([TUnion.java L230-L253](https://github.com/apache/thrift/blob/6050f83e10ae926deccf0c2aa0c0f3e90dbd54cf/lib/java/src/main/java/org/apache/thrift/TUnion.java#L230-L253)).

**GraphQL.**
- Servers must return defined enum values ([#sec-Enums.Result-Coercion](https://spec.graphql.org/October2021/#sec-Enums.Result-Coercion)). A breaking change is one that invalidates a previously valid request ([Validation](https://spec.graphql.org/October2021/#sec-Validation)), so additions are not breaking. No spec text requiring client tolerance was found (unconfirmed).
- Apollo's checks class `VALUE_ADDED_TO_ENUM` as non-breaking but warn about switches without `default`. They class `TYPE_ADDED_TO_UNION`/`INTERFACE` as non-breaking with no warning ([checks reference#schema-additions](https://www.apollographql.com/docs/graphos/platform/schema-management/checks/reference#schema-additions)).
- A new union member arrives with only `__typename` plus unconditioned fields. No Apollo page states a client rule for this (unconfirmed).

**openapi-generator `enumUnknownDefaultCase`.**
- It adds `unknown_default_open_api` so clients "can safely fallback" ([CodegenConstants.java L453-L456](https://github.com/OpenAPITools/openapi-generator/blob/df804ac9802fba0c51a64f8c3cb03191ed3dde2d/modules/openapi-generator/src/main/java/org/openapitools/codegen/CodegenConstants.java#L453-L456)). The raw value is discarded, and the sentinel cannot be sent.
- **Origin.** It started from [#1529](https://github.com/OpenAPITools/openapi-generator/issues/1529): "we like our code strongly-typed". A Swift-only version came first ([PR #11013](https://github.com/OpenAPITools/openapi-generator/pull/11013)), and it was generalised in [PR #11078](https://github.com/OpenAPITools/openapi-generator/pull/11078) (2021-12-21).
- **Coverage.** Many generators declared the case without mapping to it ([#13444](https://github.com/OpenAPITools/openapi-generator/issues/13444), [#19674](https://github.com/OpenAPITools/openapi-generator/issues/19674), [#25291](https://github.com/OpenAPITools/openapi-generator/issues/25291)). Fixes landed only in Oct 2026 ([#25331](https://github.com/OpenAPITools/openapi-generator/pull/25331), [#25332](https://github.com/OpenAPITools/openapi-generator/pull/25332), [#25266](https://github.com/OpenAPITools/openapi-generator/pull/25266), [#25344](https://github.com/OpenAPITools/openapi-generator/pull/25344)).
- `oneOf` discriminator handling was not verified.

**API guidelines.**
- **Google.** [AIP-126](https://google.aip.dev/126) puts `<ENUM>_UNSPECIFIED` first, merges any `UNKNOWN` into it, and says to use a documented string for frequently changing sets. It has no client-tolerance rule. [AIP-180](https://google.aip.dev/180#adding-components) warns that "user code does not handle new values gracefully".
- **Microsoft Azure.**
  - Clients should treat extensible enums "effectively… as strings". Services MAY return unknown values but SHOULD NOT accept them, and discriminators SHOULD be extensible enums ([Guidelines.md L432-L440](https://github.com/microsoft/api-guidelines/blob/1c58ca7f1eb51768cb4e21facd6ce0154ee4db64/azure/Guidelines.md#L432-L440)). What clients do with an unknown `kind` is unconfirmed.
  - AutoRest's `modelAsString: true` means "No validation will happen" ([autorest extensions#x-ms-enum](https://github.com/Azure/autorest/blob/main/docs/extensions/readme.md#x-ms-enum)).
- **Stripe.** Open enums grow without a version bump, and clients "should include a safe fallback". For requests, "Stripe validates request values" ([api/enums](https://docs.stripe.com/api/enums)). The older list of backward-compatible changes no longer appears on [docs.stripe.com/upgrades](https://docs.stripe.com/upgrades) (unconfirmed).

### 4.5 Telegram Bot API and Telegram libraries

**What Telegram guarantees.**
- There is no explicit forward-compatibility rule, only hedges: "Currently, can be …" ([#messageentity](https://core.telegram.org/bots/api#messageentity)), "Currently, the following 6 types of chat members are supported" ([#chatmember](https://core.telegram.org/bots/api#chatmember)), and "Currently, it can be one of" on ReactionType, BackgroundType, PaidMedia, StoryAreaType and others.
- The default `allowed_updates` excludes `chat_member` and `message_reaction*` ([#getupdates](https://core.telegram.org/bots/api#getupdates)).
- New entity types ship in minor releases: `date_time` ([2026-03-01](https://core.telegram.org/bots/api-changelog#march-1-2026)), `ton_address` and `bank_card_number` ([2026-11-09](https://core.telegram.org/bots/api-changelog#november-9-2026)), `expandable_blockquote` ([2024-05-28](https://core.telegram.org/bots/api-changelog#may-28-2024)) and `blockquote` ([2023-12-29](https://core.telegram.org/bots/api-changelog#december-29-2023)).
- Telegram's own compatibility practice is server-side: it keeps old and duplicate fields "for backward compatibility" ([changelog](https://core.telegram.org/bots/api-changelog)).

## 5. Implications for Telegramium

These are readings of the evidence, not decisions.

- **Wrapper vs in-enum: both are well precedented; the wrapper has the closest analogues.** In-enum cases dominate generated code (ScalaPB, smithy4s, Caliban, smithy-rs, smithy-kotlin, swift-protobuf). But the maintainer's concern, generic code forgetting an `Unknown` buried in the enum, is exactly what several in-enum libraries patched after the fact. ScalaPB added `Recognized` and narrowed `values`, Apollo Kotlin added `__Known`, and amazonka deleted `Bounded`/`Enum`. Apollo iOS moved from per-enum `__unknown` to `GraphQLEnum<T>`, which is structurally `OpenEnum`. enumeratum's maintainer proposed the same wrapper and called the per-enum case a "tax". proto-lens #150 is not evidence against a wrapper: its complaint was a newtype that lost exhaustiveness, and `OpenEnum[T]` keeps `T` closed and sealed. The evidence leans toward the wrapper.
- **An object family's `Unknown` should keep the whole payload if it may be sent back.** Every library that can re-send an unknown variant keeps the whole object: smithy4s `@jsonUnknown` writes the entire document back, python-telegram-bot re-emits `api_kwargs`, Telegram.Bot `RichTextUnsupported` holds a `JsonDocument`, and teloxide stores a `Value`. Libraries that keep only the tag (smithy-rs, smithy-kotlin, AWS Java) refuse to serialize the unknown union, which is the #723 failure. `Unknown(value, raw: Json)` matches the payload-keeping group.
- **Write the raw payload back verbatim, without re-wrapping it.** smithy4s writes the catch-all without a tag wrapper. FsCodec, which nests the element under its own case name, does not reproduce the original.
- **The object-family fallback must not swallow malformed known variants.** circe's `Decoder.or` and teloxide's `.ok()` both conflate "unknown tag" with "known tag that failed to decode". The evidence suggests choosing `Unknown` only when the tag is not a known one.
- **A string enum's `Unknown` needs only the string.** For a scalar enum the string is the whole wire value. Every open string enum surveyed (smithy4s, Apollo iOS, smithy-kotlin, Caliban, atdgen, amazonka, AWS Java, Stripe) stores just the string, and none stores JSON. The only precedent for a single unknown case with an optional JSON payload, atdgen's `Unknown of (string * json option)`, was removed in 2.0, with no rationale found. A `raw: Json` holding a JSON string would duplicate `value`, which supports the maintainer's irritation.
- **Typing `Chat.type` and similar is supported, as long as the type is open.** The cautionary cases are closed types: bot4s's `ChatType` throws, canoe's `Chat` is closed, and telegram-bot-simple, teloxide and bot4s lose whole updates. smithy4s's docs and AIP-126 note that a plain string can suit fast-changing sets. Telegram's "Currently, can be …" wording and its record of minor-release additions mean any typed version must be open.
- **Keep `Unknown` out of `values`.** This is unanimous across the surveyed libraries. With a wrapper it comes for free, because `T`'s `values` contains no unknown.
- **Hand-built `Unknown` values should be allowed, for sending.** Smithy makes sending unknown enum values a MUST, and #723 itself requires re-sending. Telegram may still reject values it doesn't know, just as Microsoft and Stripe services validate their inputs.
- **Hand-built `Unknown` values need a rule for equality.** The risk is `Unknown("bold")` coexisting with `Known(Bold)`, which breaks equality and silently changes behaviour once a library upgrade makes the value known (smithy-rs #627). Precedent offers three remedies:
  - restrict construction: smithy-rs's opaque payload, Apollo Kotlin 4's private constructor, protobuf-java throwing on `setX(UNRECOGNIZED)`, proto-lens's hidden constructor;
  - normalise on construction: smithy-rs `From<&str>`, Apollo Kotlin `safeValueOf`;
  - compare raw values: Apollo iOS.

  A normalising smart constructor satisfies both needs: values can still be sent, and aliasing is ruled out. The notes do not cover equality for object-family `Unknown`s that carry `raw` JSON.

## 6. Open or unverified points

- **Corrections and conflicts.**
  - An earlier claim that smithy4s unions are always closed is wrong: `01-scala.md` shows opt-in open unions via `@jsonUnknown` + `Document` since 0.18.35. What is true is that smithy4s rejects Smithy's open-by-default unions.
  - Each note's "only X keeps union payloads" is scoped to its own ecosystem: smithy4s and protobuf (Scala), FsCodec (ML, not faithful), teloxide and protobuf (mainstream), PTB and Telegram.Bot (Telegram). Together they form the set in section 2.
  - `01-scala.md` says a wrapper was "proposed by only one maintainer" (enumeratum). That holds within Scala; across ecosystems Apollo iOS and proto3-suite ship wrappers.
  - The task brief's claim that AIP-126 has a client-tolerance rule was not confirmed.
- **Inferences that were not tested.**
  - zio-aws hiding the raw string at runtime, and whether it has a String setter.
  - amazonka unions decoding to all-`Nothing`.
  - serde untagged `Unknown(Value)` capturing payloads.
  - teloxide unknown service messages landing in `Empty {}`.
  - The protobuf-go oneof being nil.
  - aiogram rejecting an unknown status.
  - telegram-bot-simple refetching trailing updates.
  - FsCodec's non-faithful re-encode, which was read from source.
- **Behaviour that was not verified.**
  - Apollo iOS with an unknown `__typename` in object unions.
  - Stripe TS narrowing with `OtherString`.
  - C# protobuf with an unknown oneof member.
  - openapi-generator `oneOf` discriminators.
  - proto3-suite unknown fields.
  - Telegram.Bot re-serializing `RichTextUnsupported` identically.
- **Spec gaps.**
  - Thrift: whether a normative rule exists outside the IDL doc.
  - GraphQL: any client-tolerance rule.
  - Microsoft: what clients do with an unknown `kind`.
  - Stripe: the removed list of backward-compatible changes.
  - grammY: the meaning of "Those types are not closed".
- **No design discussion found.** Nothing was found for circe, zio-json, Scala 3 enums, aeson's built-in fallback, ocaml-protoc, or atdgen's removal of `untyped`.
- **JSON limits protobuf's guarantees.** Protobuf's lossless guarantees are mostly binary: ProtoJSON drops unknown fields, and swift-protobuf and proto3-suite fail on unknown enum names in JSON. Protobuf precedents transfer to Telegram's JSON only partly.
