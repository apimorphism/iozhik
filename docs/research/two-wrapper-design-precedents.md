# Precedents for a two-wrapper design (`OpenEnum` + `OpenUnion`)

## 1. Question and scope

Telegramium has settled, on paper and in a spike, on two separate generic wrappers:

- `OpenEnum[+T]` with `Known(value: T)` and `Unknown(value: String)`, for open string enums such as `Chat.type`;
- `OpenUnion[+T]` with `Known(value: T)` and `Unknown(tag: String, raw: Json)`, for tagged-object families such as MessageEntity and ChatMember.

The maintainer asks whether this two-fold design is common, and where it is found. This document answers six questions: who has two mechanisms side by side, who uses one wrapper for both, where a generic wrapper around a union exists at all, what names are in use, what history exists of splitting or merging, and what costs users reported.

It extends [forward-compatible-enums.md](forward-compatible-enums.md) ("the existing doc") and does not repeat it. Researched on 2026-11-13. Links are pinned to the commits that were read. "Verified" means read in the linked source; "inference" means concluded from the source without running it.

## 2. Summary for the decision

**Direct answer.** The *split by payload* is common: almost every library that keeps unknown values for both kinds keeps a bare string (or int) for enums and a JSON value for object variants. The *two generic wrapper types* are rare. No library was found that ships exactly `Wrapper[T] = Known(T) | Unknown(String)` next to `Wrapper[T] = Known(T) | Unknown(tag, raw)`. A generic `Known | Unknown(payload)` wrapper around a union, as opposed to an extra case inside it, was found in only two places, and neither is a dedicated union wrapper (Stainless `JsonField<T>`, Swift OpenAPI Generator's `anyOf` struct). The dominant shape for unions is an in-type unknown case or subclass.

**Closest precedents, ranked.**

1. **Speakeasy TypeScript runtime** (verified). Two distinct generic types in the same runtime directory: `OpenEnum<T>` (known literals, or a branded `Unrecognized<string>`) and `Unknown<Discriminator>` (`{ [discriminator]: "UNKNOWN", raw: unknown, isUnknown: true }`), produced by a generic `discriminatedUnion(...)` parser. This is the only find with two named generic mechanisms. They are TypeScript union members, so known values are not wrapped, and the unknown side replaces the tag with `"UNKNOWN"` and leaves the original tag inside `raw`.
2. **ktgbotapi** (Kotlin, Telegram Bot API; verified). Same domain and the same payload split, as in-type cases: `StickerType.Unknown(type: String)` for string enums; `Reaction.Unknown(type: String, sourceJson: JsonElement?)`, `BackgroundType.Unknown(type, raw: JsonElement?)` and others for object families, with the stored JSON written back on serialize. The `(type, raw)` field pair is the same as `OpenUnion.Unknown(tag, raw)`.
3. **Swift OpenAPI Generator** (verified). 0.1.x generated in-type cases with the same split: `undocumented(String)` on enums, `undocumented(OpenAPIValueContainer)` or `undocumented(OpenAPIObjectContainer)` on oneOfs. 0.2.0 removed them. The documented replacement is a wrapper-shaped struct for both kinds, generated from `anyOf: [closed type, raw type]`, with `value1` (known) and `value2` (raw string, or raw JSON container). This is the closest thing to a known-or-raw wrapper around a union, and it uses one mechanism for both kinds.
4. **Stainless and Fern Java SDKs** (verified on anthropic-sdk-java and square-java-sdk). Per-type generated classes, two different shapes: enums carry `Known` and `Value { ..., _UNKNOWN }` views over the raw string; unions carry the raw JSON (`_json: JsonValue`, `_UnknownValue`) behind a visitor `unknown(...)` method, and write it back. Stainless also has one generic `JsonField<T>` = `KnownValue<T>` | `JsonValue` under every field.

Also close on the union side alone: **AWS SDK Go v2** `UnknownUnionMember { Tag string; Value []byte }`, one shared struct for all unions of a service, with exactly the tag-plus-raw-bytes pair (verified).

**What else the evidence shows.**

- **Payload types differ between the two sides everywhere that both are kept.** ktgbotapi, slack-morphism (`Other(String)` and `Unknown(serde_json::Value)` in one file), async-stripe (`Unknown(String)` and `EventObject::Unknown(Value)`), serenity (`Unknown(u8)` and `UnknownEvent { kind, value }`), Swift OpenAPI 0.1.x, Fern and Stainless all use a scalar for enums and JSON for objects. No library was found with a single unknown case type whose payload is a type parameter. The one single generic type that covers both, Stainless `JsonField<T>`, always stores JSON and represents an unknown scalar as a JSON string node.
- **Azure and AWS show the asymmetric alternative again.** Azure C# uses a string-backed struct for enums and an internal `Unknown<Base>` subclass for discriminated types; Azure Java uses `ExpandableStringEnum<T>` and falls back to the base class. Neither exposes a wrapper.
- **The fallback often swallows malformed known variants, by design.** Stainless Java, Speakeasy and slack-morphism all route "known tag, body failed to parse" to the unknown case, and slack-morphism documents and tests it. This is the trap named in the existing doc (section 5), chosen deliberately by three generators.
- **A wrapper has a reported cost.** Apollo iOS users called `case .case(.someEnumCase)` "really not ideal" and asked to drop `GraphQLEnum` once Swift gets extensible enums ([#2678](https://github.com/apollographql/apollo-ios/issues/2678), [#3584](https://github.com/apollographql/apollo-ios/issues/3584)).
- **A default-open type has a reported cost.** Swift OpenAPI Generator removed its default `undocumented` case because nested enums and oneOfs "successfully" parsed into it and masked the right alternative ([#204](https://github.com/apple/swift-openapi-generator/issues/204)).

## 3. Comparison table

"Same or different" compares the enum-side and union-side mechanisms. "Re-serializable" is about the union side.

|---|---|---|---|---|---|---|
| Speakeasy TS (mistralai/client-ts) | generic `OpenEnum<T>` = literals \| `Unrecognized<string>` | generic `Unknown<Discriminator>` member added by `discriminatedUnion()` | different generic types, same runtime | whole input in `raw`; tag overwritten with `"UNKNOWN"` | not verified (inbound schema only was read) | `OpenEnum`, `ClosedEnum`, `Unrecognized`, `Unknown`, `raw`, `isUnknown` |
| ktgbotapi | in-type `Unknown(type: String)` | in-type `Unknown(type, raw/sourceJson/source: JsonElement?)` | different, per family | tag + whole JSON | yes, writes stored JSON | `Unknown`, `UnknownChatType`, `raw`, `rawJson`, `sourceJson`, `source` |

## 4. Per-ecosystem findings

### 4.1 Generated API SDKs (Speakeasy, Stainless, Fern)

**Speakeasy (TypeScript, read in mistralai/client-ts).** Verified.

- **Enums.** `OpenEnum<T> = T[keyof T] | Unrecognized<string | number>`, next to `ClosedEnum<T>` ([enums.ts L8-L12](https://github.com/mistralai/client-ts/blob/3e87497eea3ae73f482cd683b043469e72f12389/src/types/enums.ts#L8-L12)). `Unrecognized<T>` is a branded alias, `T & { [__brand]: "unrecognized" }` ([unrecognized.ts L5-L6](https://github.com/mistralai/client-ts/blob/3e87497eea3ae73f482cd683b043469e72f12389/src/types/unrecognized.ts#L5-L6)). The value is the raw string at runtime; only the type marks it. Generated enums are declared as `type Source = OpenEnum<typeof Source>`.
- **Unions.** `Unknown<Discriminator, UnknownValue = "UNKNOWN">` is `{ [discriminator]: "UNKNOWN", raw: unknown, isUnknown: true }` with an `isUnknown()` guard ([discriminatedUnion.ts L10-L23](https://github.com/mistralai/client-ts/blob/3e87497eea3ae73f482cd683b043469e72f12389/src/types/discriminatedUnion.ts#L10-L23)). A generic `discriminatedUnion(inputPropertyName, options)` parser is documented as "Forward-compatible discriminated union parser" ([L25-L53](https://github.com/mistralai/client-ts/blob/3e87497eea3ae73f482cd683b043469e72f12389/src/types/discriminatedUnion.ts#L25-L53)). Generated types read `BaseModelCard | FTModelCard | discriminatedUnionTypes.Unknown<"type">` ([modellist.ts L14-L17](https://github.com/mistralai/client-ts/blob/3e87497eea3ae73f482cd683b043469e72f12389/src/models/components/modellist.ts#L14-L17)).
- **Tag handling.** The discriminator field of the unknown member is set to the constant `"UNKNOWN"`, so the original tag is only inside `raw` ([L56-L63](https://github.com/mistralai/client-ts/blob/3e87497eea3ae73f482cd683b043469e72f12389/src/types/discriminatedUnion.ts#L56-L63)).
- **Malformed known variants.** A known discriminator whose body fails `safeParse` also returns the fallback ([L78-L84](https://github.com/mistralai/client-ts/blob/3e87497eea3ae73f482cd683b043469e72f12389/src/types/discriminatedUnion.ts#L78-L84)).
- Not checked: whether an `Unknown` member can be sent back, and Speakeasy's other target languages.

**Stainless (Java/Kotlin, read in anthropics/anthropic-sdk-java).** Verified.

- **Generic substrate.** `sealed class JsonField<out T>` is "either a `KnownValue` value of type `T`, matching the type the SDK expects, or an arbitrary JSON value that bypasses the type system (via `JsonValue`)", with `asKnown()` and `asUnknown()` ([Values.kt L34-L71](https://github.com/anthropics/anthropic-sdk-java/blob/79d1eda51e72bcf6236520e575e5761838d5c1ea/anthropic-java-core/src/main/kotlin/com/anthropic/core/Values.kt#L34-L71)). `JsonValue` extends `JsonField<Nothing>` and is "assignable to any `JsonField`, regardless of its expected type" ([L266-L273](https://github.com/anthropics/anthropic-sdk-java/blob/79d1eda51e72bcf6236520e575e5761838d5c1ea/anthropic-java-core/src/main/kotlin/com/anthropic/core/Values.kt#L266-L273)). This is the same variance trick as `Unknown extends OpenEnum[Nothing]`.
- **Enums.** Each enum is a class over `JsonField<String>` with a nested `enum class Known`, a nested `enum class Value` that adds `_UNKNOWN`, `value()` (total), `known()` (throws on unknown) and `asString()` ([StopReason.kt L9](https://github.com/anthropics/anthropic-sdk-java/blob/79d1eda51e72bcf6236520e575e5761838d5c1ea/anthropic-java-core/src/main/kotlin/com/anthropic/models/messages/StopReason.kt#L9), [L58-L138](https://github.com/anthropics/anthropic-sdk-java/blob/79d1eda51e72bcf6236520e575e5761838d5c1ea/anthropic-java-core/src/main/kotlin/com/anthropic/models/messages/StopReason.kt#L58-L138)). The kdoc names both sources of an unknown: newer API, or "constructed with an arbitrary value using the `of` method".
- **Unions.** Each union is a class with one nullable field per variant plus `_json: JsonValue?` ([ContentBlock.kt L26-L41](https://github.com/anthropics/anthropic-sdk-java/blob/79d1eda51e72bcf6236520e575e5761838d5c1ea/anthropic-java-core/src/main/kotlin/com/anthropic/models/messages/ContentBlock.kt#L26-L41)). `Visitor.unknown(json: JsonValue?)` throws unless overridden ([L484-L495](https://github.com/anthropics/anthropic-sdk-java/blob/79d1eda51e72bcf6236520e575e5761838d5c1ea/anthropic-java-core/src/main/kotlin/com/anthropic/models/messages/ContentBlock.kt#L484-L495)). The serializer writes `_json` back for the unknown variant ([L598](https://github.com/anthropics/anthropic-sdk-java/blob/79d1eda51e72bcf6236520e575e5761838d5c1ea/anthropic-java-core/src/main/kotlin/com/anthropic/models/messages/ContentBlock.kt#L598)).
- **Malformed known variants.** `tryDeserialize(node, …)?.let { ContentBlock(text = it, _json = json) } ?: ContentBlock(_json = json)`: a known `type` that fails to deserialize becomes the unknown variant ([L497-L507](https://github.com/anthropics/anthropic-sdk-java/blob/79d1eda51e72bcf6236520e575e5761838d5c1ea/anthropic-java-core/src/main/kotlin/com/anthropic/models/messages/ContentBlock.kt#L497-L507)).
- **Go.** Enums are `type StopReason string` ([message.go L12208](https://github.com/anthropics/anthropic-sdk-go/blob/eba55420edf6d9ee276722cf7b6d001c602ff44d/message.go#L12208)). Unions are one flattened struct with a `Type string` field and an `AsAny()` switch whose documented default is "no variant present" ([message.go L6895-L6931](https://github.com/anthropics/anthropic-sdk-go/blob/eba55420edf6d9ee276722cf7b6d001c602ff44d/message.go#L6895-L6931)).
- The OpenAI Java and Go SDKs come from the same generator; they were not read separately (inference that they match).

**Fern (Java, read in square/square-java-sdk).** Verified.

- **Enums.** A final class holding `Value` and the raw `String`; unknown strings become `new Currency(Value.UNKNOWN, value)`, and the visitor gets `visitUnknown(string)` ([Currency.java L773-L775](https://github.com/square/square-java-sdk/blob/133dbb7db61e4956974807f8d8f18247671df85f/src/main/java/com/squareup/square/types/Currency.java#L773-L775), [L1149](https://github.com/square/square-java-sdk/blob/133dbb7db61e4956974807f8d8f18247671df85f/src/main/java/com/squareup/square/types/Currency.java#L1149)). The same enum also has an API value `UNKNOWN_CURRENCY` beside the generated `UNKNOWN` ([L1153-L1154](https://github.com/square/square-java-sdk/blob/133dbb7db61e4956974807f8d8f18247671df85f/src/main/java/com/squareup/square/types/Currency.java#L1153-L1154), [L1520](https://github.com/square/square-java-sdk/blob/133dbb7db61e4956974807f8d8f18247671df85f/src/main/java/com/squareup/square/types/Currency.java#L1520)), which shows the name collision that in-enum cases invite.

### 4.2 Swift

**Swift OpenAPI Generator.** Verified.

- **0.1.x.** Enums had `case undocumented(String)`; oneOfs had `case undocumented(OpenAPIRuntime.OpenAPIValueContainer)`, or `OpenAPIObjectContainer` when a discriminator makes the payload an object; both were re-encoded ([0.1.8 Petstore Types.swift L112](https://github.com/apple/swift-openapi-generator/blob/0.1.8/Tests/OpenAPIGeneratorReferenceTests/Resources/ReferenceSources/Petstore/Types.swift#L112), [L460-L488](https://github.com/apple/swift-openapi-generator/blob/0.1.8/Tests/OpenAPIGeneratorReferenceTests/Resources/ReferenceSources/Petstore/Types.swift#L460-L488), [L568-L586](https://github.com/apple/swift-openapi-generator/blob/0.1.8/Tests/OpenAPIGeneratorReferenceTests/Resources/ReferenceSources/Petstore/Types.swift#L568-L586)).
- **0.2.0 onwards.** The cases are gone; an unknown discriminator throws `unknownOneOfDiscriminator` ([translateCodable.swift L284-L289](https://github.com/apple/swift-openapi-generator/blob/fbf4512ebc69ccbca33aa3c5fa4393887e687b76/Sources/_OpenAPIGeneratorCore/Translator/CommonTranslations/translateCodable.swift#L284-L289)). Openness is opted into in the schema, with the same pattern for both kinds: `anyOf: [enum, {type: string}]` and `anyOf: [oneOf, {}]` (or `{type: object}` "if you know the payload is … always a JSON object"). The reader checks the first value, and "if the enum value is nil, the second string value will contain the raw value" ([Useful-OpenAPI-patterns.md L9-L74](https://github.com/apple/swift-openapi-generator/blob/fbf4512ebc69ccbca33aa3c5fa4393887e687b76/Sources/swift-openapi-generator/Documentation.docc/Articles/Useful-OpenAPI-patterns.md#L9-L74)).
- `undocumented` survives for HTTP responses and multipart parts ([Constants.swift L280-L284](https://github.com/apple/swift-openapi-generator/blob/fbf4512ebc69ccbca33aa3c5fa4393887e687b76/Sources/_OpenAPIGeneratorCore/Translator/CommonTypes/Constants.swift#L280-L284)).

**Apollo iOS 1.x.** Verified; this closes an open point of the existing doc.

- There is no wrapper on the union side. A selection set exposes `__typename: String?`; `__objectType` returns nil when the schema has no such type; `asX` accessors (`_asInlineFragment`) return nil when the fragment is not fulfilled ([SelectionSet.swift L100-L128](https://github.com/apollographql/apollo-ios/blob/fea2613e7d69dbf532b5aad897722be638f345be/Sources/ApolloAPI/SelectionSet.swift#L100-L128)). For cache purposes an unknown typename becomes `Object(typename: typename, implementedInterfaces: [])` ([SchemaMetadata.swift L19-L44](https://github.com/apollographql/apollo-ios/blob/fea2613e7d69dbf532b5aad897722be638f345be/Sources/ApolloAPI/SchemaMetadata.swift#L19-L44)).
- So Apollo iOS has a generic wrapper for enums and no dedicated mechanism for unions. GraphQL makes this natural: a response contains only the fields the query selected, so there is no opaque payload to keep.

**AWS SDK for Swift.** Verified. Enums get `case sdkUnknown(Swift.String)` holding the raw value ([Models.swift L179-L209](https://github.com/awslabs/aws-sdk-swift/blob/f71893b7ee03dd4857d636c2a0606966a7201756/Sources/Services/AWSBedrockRuntime/Sources/AWSBedrockRuntime/Models.swift#L179-L209)). Unions get the same case name, but it holds only the member name (`return .sdkUnknown(name ?? "")`), and the writer emits a member literally called `sdkUnknown` ([L7036-L7056](https://github.com/awslabs/aws-sdk-swift/blob/f71893b7ee03dd4857d636c2a0606966a7201756/Sources/Services/AWSBedrockRuntime/Sources/AWSBedrockRuntime/Models.swift#L7036-L7056)). The same name for both sides hides different meanings.

## 6. History and reported costs

**History (question 5).**

- **Swift OpenAPI Generator: in-type cases for both, then removed in favour of a schema-level wrapper pattern.** Issue [#204](https://github.com/apple/swift-openapi-generator/issues/204) (Aug 2023): "It seemed like a good idea to generate the undocumented case before, as it allows for API evolution… However, OpenAPI/JSON Schema enums/oneOfs are closed by default, so we're actually diverging from the specification here. And it's causing issues when these enums/oneOfs are nested within other allOfs/oneOfs/anyOfs and it 'successfully' parses even though it parses into an undocumented case." [PR #205](https://github.com/apple/swift-openapi-generator/pull/205) added a `closedEnumsAndOneOfs` flag and announced that "in 0.2.0 we'll stop generating `undocumented` cases unconditionally". The enum and oneOf sides were added together and removed together; they were never split or merged.
- **Apollo iOS: per-enum case, then a generic wrapper, with a request to go back.** The move to `GraphQLEnum<T>` in 1.0 is in the existing doc. [#3584](https://github.com/apollographql/apollo-ios/issues/3584) (open, Sep 2025) asks to use Swift extensible enums so that "you could drop the GraphQLEnum type, eventually".
- **TypeSpec: extensible enums moved from `enum` to `union`.** The April 2024 release notes record "enums are always fixed after we switch to use union to represent extensible enum" ([release-2024-04-02.md L20](https://github.com/Azure/typespec-azure/blob/ada84742922514af04da16e559ca15bea2b37c4a/website/src/content/docs/docs/release-notes/release-2024-04-02.md#L20)). This merges the *schema-language* concept of an open enum into unions; the generated C# and Java types stayed separate.
- **atdgen: one unknown case with an optional JSON payload, removed.** Existing doc, section 4.2. This remains the only found case of a single shape for both that was dropped, and no rationale was found.
- **No library was found that started with one type for both and split, or started split and merged,** on the client-type level.

**Reported costs (question 6).**

- **Wrapper verbosity (Apollo iOS).** From the 1.0 migration feedback thread [#2678](https://github.com/apollographql/apollo-ios/issues/2678): "Having to add `case .case(.someEnumCase)` for every case to get an exhaustive switch isn't a great experience", and "While the old codegen creating `__unknown` always looked a little weird, it allowed a simple way to create exhaustive switch statements with the case names directly." A second user: "having `case .case(.someEnumCase)` is really not ideal, and fixing this all over my codebase was probably where I spent the majority of my time".
- **Convenience matching defeats exhaustiveness (Apollo iOS).** Same thread: "The custom pattern matching on `GraphQLEnum` can't be used while also making a switch statement exhaustive. A `default` case is always required". The maintainer agreed ("we are aware of this limitation") and recommended a nested switch or `.value`. [#3584](https://github.com/apollographql/apollo-ios/issues/3584) restates it: "you have to dance around either: switching directly on the GraphQLEnum<Enum>, which requires a default case; unwrapping directly the enum and exhaustively checking."
- **Wrapper and test mocks (Apollo iOS).** Several issues report crashes or failures when passing `GraphQLEnum` values to generated mocks ([#2582](https://github.com/apollographql/apollo-ios/issues/2582), [#2686](https://github.com/apollographql/apollo-ios/issues/2686), [#2928](https://github.com/apollographql/apollo-ios/issues/2928), [#2970](https://github.com/apollographql/apollo-ios/issues/2970)). Only the titles were read.
- **Class-based unions are awkward to match (Stainless Java).** [openai-java #545](https://github.com/openai/openai-java/issues/545): "you have to do things like `if (event.isOutputTextDelta()) { … } else if (event.isCompleted()) { … }`", with a request for real enums or a sealed hierarchy so that `switch` works. The reporter keeps a hand-written enum with an `UNKNOWN` member as a workaround.
- **Unknown fallback masks the right alternative when nested (Swift OpenAPI).** Quoted above from #204.
- **Equality and raw-string comparison.** Nothing new was found beyond smithy-rs #627 in the existing doc. Azure C# sidesteps the question by making the enum a string-backed struct with implicit conversion and case-insensitive `Equals`.
- **Codec derivation problems caused by a wrapper.** None found.

## 7. Implications for Telegramium

These are readings of the evidence, not decisions.

- **The payload split is the norm, so two different `Unknown` shapes are well supported.** Wherever a library keeps both, the enum side holds a scalar and the object side holds JSON. A single `Unknown(value, raw)` for both, the earlier option (a), has one removed precedent (atdgen) and one living relative (Stainless `JsonField<T>`, which always stores JSON).
- **Two generic wrapper types is a design with one near precedent.** Speakeasy's `OpenEnum<T>` and `Unknown<Discriminator>` are two named generic mechanisms, but they add a member to a TypeScript union and do not wrap the known side. A Scala `OpenUnion[T]` that wraps `Known(value)` has no direct counterpart; the usual choice is an unknown case inside the family (ktgbotapi, serenity, slack-morphism, Kord, JDA, AWS Go and JS, Azure C#, Fern, Stainless). Telegramium's reason for a wrapper on the enum side (generic code forgetting a buried case, existing doc section 5) applies to unions too, but the evidence base for it is on the enum side.
- **`Unknown(tag, raw)` matches what payload-keeping libraries store.** ktgbotapi (`type` + `raw`), serenity (`kind` + `value`) and AWS Go (`Tag` + `Value`) keep the tag as a separate field next to the payload. Speakeasy keeps only `raw` and overwrites the tag. Keeping `tag` separately duplicates data that is inside `raw`, which those three libraries accept.
- **The wrapper's known cost is matching verbosity.** Apollo iOS users objected to `.case(.x)` on every arm, which corresponds to `Known(X)` in Scala. Scala pattern matching on `Known(ChatType.Private)` stays exhaustive without a custom operator, so the second Apollo complaint (convenience matching losing exhaustiveness) arises only if Telegramium adds an `==`-style shortcut against raw values.
- **Decide deliberately what a malformed known variant becomes.** Stainless, Speakeasy, slack-morphism and ktgbotapi's helper send it to the unknown case; the existing doc flagged that as a trap. Three generators choosing it suggests it is a considered trade (never fail a response) and not an accident. `OpenUnion.Unknown(tag, raw)` cannot distinguish the two situations unless the decoder refuses the fallback for known tags.
- **A default-open union can hide a better parse.** Swift OpenAPI's problem arose when open types sat inside `anyOf`/`oneOf` alternatives tried in order. Telegram's tagged families are selected by a discriminator, not by trial, so this applies only where Telegramium decodes untagged alternatives (inference).
- **On the name.** "Open" is established for enums and is used for unions by TypeSpec ("open union") and Swift OpenAPI ("open oneOf"). Nobody ships a type called `OpenUnion`. The common terms for the family are "union", "discriminated union" and "tagged union"; "polymorphic" is the JVM serializers' word.
- **A shared wrapper fixes field names once.** ktgbotapi, with per-family cases, ended up with four names for the raw payload and with families that have no unknown case at all (`ChatMember`). That is an argument for a generic mechanism over hand-written per-family cases, whichever shape it takes.

## 9. Design discussions: was a wrapper considered and rejected?

Researched on 2026-11-13. Sections 1 to 8 looked at what libraries ship. This section looks for the issues, PRs, RFCs and design docs in which the unknown-value representation was designed, to see whether a generic wrapper (around a union or an enum) was considered and turned down, or never came up. "Verified" means the quoted text was read in the linked thread or file; "inference" is marked as such. Silence is reported as silence, not as a rejection.

### 9.1 Summary

**Direct answer.** For unions, the question mostly never came up. In smithy-rs, smithy-kotlin, smithy4s, ktgbotapi, serde, proto-lens and Swift OpenAPI the in-family unknown case was the first and only design written down, and nobody proposed a wrapper around the union. Only two projects put such a wrapper on paper, and neither rejected it with a reason. **Apollo iOS's 1.0 RFC specified a generic `Union<UnionType>` wrapper "that provides access to the underlying `UnionType` and unknown cases"**, next to `GraphQLEnum<T>`, and then shipped without it; no record of why survives. **ScalaPB weighed an `Option` wrapper around oneofs** (whose unknown members decode to `Empty`) and chose a `NonEmpty` sub-trait by default. The reasons were source compatibility, not "generating very different APIs", and `Seq[Option[…]]` for repeated fields. Scalameta's olafurpg added that `Option` makes "both construction and pattern matching more complicated". ScalaPB later added the wrapper anyway as an opt-in style. FIDL listed an `Option`-like "optional flexible unions" alternative without rebutting it. For enums the question did come up, and the wrapper did well: enumeratum's maintainer rejected the in-enum case as an "exhaustive-pattern-checking tax" and proposed `EnumOrUnknown`, with no objection.

**What the reasons were, where reasons exist.**

- **Against keeping union payloads**, not against wrappers: smithy-kotlin ("Union members may represent any structure… unclear if providing the stringified form to customers has any value") and FIDL RFC-0137, which removed payload keeping after a year: little use, migration and binding complexity, security, and proxying rarely survives conversion to application types.
- **For keeping them**: smithy-go ("Necessary for re-serialization"). It also chose one shared `UnknownUnionMember` struct for all unions because "The definition between them will not change".
- **Against a wrapper**: construction and matching noise, a second API flavour to maintain, and `Seq[Option[T]]` (ScalaPB); per-query code size (Apollo iOS, for payload-carrying union enums); a user's wish not to "expose a wrapper type" (serde). Apollo Kotlin's maintainer was wary of "handling `UNKNOWN__` globally" but shipped generic interfaces anyway.
- **For a wrapper**: the in-enum case is a "tax" and conflicts with `findValues` (enumeratum); unknowns can be handled once (Apollo Kotlin user). In Apollo iOS the wrapper exists only because a Swift enum with an associated-value case loses `RawValue` and synthesized `Equatable`/`Hashable`; the maintainer would rather drop it.
- **Common middle path**: a known-only sub-type inside the family, such as ScalaPB `Recognized`/`NonEmpty` and Apollo Kotlin `__Known`. It was chosen twice explicitly as the cheaper alternative to a wrapper, because it adds the "unwrap once" property without changing field types.

**New find.** A generated SDK does ship a generic union wrapper: oh-my-pi's Rust RPC types use `OrUnknown<T> = Known(T) | Unknown { raw, error }` around a discriminated union field, next to in-family `Unknown(Value)` cases elsewhere (section 9.4).

**Contradictions with earlier sections.** Section 2 says a generic wrapper around a union "was found in only two places". Add oh-my-pi's `OrUnknown<T>` (shipped) and Apollo iOS's `Union<UnionType>` (specified, not shipped). Section 8 says no rationale was found for AWS Go keeping payloads; one is now found (re-serialization, smithy-go commit 8f16276). Section 4.2 describes Apollo iOS unions as having "no wrapper on the union side"; that holds for the shipped code, but the design document planned one.

### 9.3 Per-library findings

**ScalaPB.**

- **`Unrecognized` (2015): no discussion.** [Issue #11](https://github.com/scalapb/ScalaPB/issues/11), opened by the maintainer, says only "If we are trying to parse a message with an unknown enum value, mergeFrom raises a MatchError", and has no comments. It was closed by commit [e3cd8b1](https://github.com/scalapb/ScalaPB/commit/e3cd8b1fb2ed684543c313ed119a623fa2a01096), message "Support enums with unknown value. Fixes #11". No alternative shape was discussed (verified: issue, comments and commit message read). Outcome (c).
- **Keeping `Unrecognized` (2017).** In [#357](https://github.com/scalapb/ScalaPB/issues/357) a user asked for an option to disable it. The maintainer's reason for keeping the case is about information, not shape: "It's important that the case class preserves the unrecognized value so that the information is not lost… if the message is serialized, the serializer encodes that unrecognized value" ([comment](https://github.com/scalapb/ScalaPB/issues/357#issuecomment-337054760)). A wrapper was not mentioned (verified).
- **The `Recognized` sub-trait came from a discussion about oneofs, in which an `Option` wrapper was weighed.** The protobuf oneof's `Empty` case is the analogue of an unknown case here: an unknown oneof member decodes to `Empty` (section 4.1 of the existing doc). In [#633](https://github.com/scalapb/ScalaPB/issues/633) (2019) a user proposed three shapes to get rid of `Empty`: (1) type the field `Option[NonsealedValue]`, (2) throw, or later (3) a supertype `MyADT.Nullable` with `Empty` outside `MyADT`. The motivation: "If I have an instance of `NonsealedValue`, I want to be _really_ sure that I indeed have an actual `NonsealedValue`, not `Empty`… have `NonsealedValue` in an `Option` where I can _just once_ [check] that it's `Some`" ([comment](https://github.com/scalapb/ScalaPB/issues/633#issuecomment-522717611)). Verified.
  - The maintainer's reasons against the wrapper: it "needs to be provided in addition to the existing way, and it would come with additional maintenance cost and code complexity for the generator" ([comment](https://github.com/scalapb/ScalaPB/issues/633#issuecomment-522355550)); for repeated fields "we are going to end up with `Seq[Option[SealedOneof]]` - not sure if that's desirable" ([comment](https://github.com/scalapb/ScalaPB/issues/633#issuecomment-523010474)); and a breaking supertype "needs to be under a flag… I am trying to minimize options that end up generating very different APIs" ([comment](https://github.com/scalapb/ScalaPB/issues/633#issuecomment-523041123)).
  - His counter-proposal was a sub-trait, `sealed trait NonEmpty extends MyADT` plus `asOption: Option[MyADT.NonEmpty]`, because "it's an incremental improvement rather than introducing a new flavor of generated code. The downside is that we have two sealed traits around" ([same comment](https://github.com/scalapb/ScalaPB/issues/633#issuecomment-523010474)). It landed as commit [4da0801](https://github.com/scalapb/ScalaPB/commit/4da080105f4fc6a56715afcf631720bc6688d2f0) ("Add a NonEmpty marker trait to sealed oneofs").
  - Asked "Can the same thing be done for enum?", he answered: "Yes. I'd like enums and sealed oneofs to have a similar API as much as possible" ([comment](https://github.com/scalapb/ScalaPB/issues/633#issuecomment-533892645)). The enum `Recognized` sub-trait then arrived as [PR #652](https://github.com/scalapb/ScalaPB/pull/652), whose whole description is "analogous to 4da0801… and #633"; its review discussed only declaration order and name clashes (verified). So `Recognized` is the enum copy of a sub-trait chosen over a wrapper for oneofs.
  - The wrapper was not rejected outright in the end. After more pressure the maintainer added an opt-in `sealed_value_optional` style in which a field becomes `Option[Expr]` and a repeated field `Seq[Option[Expr]]`, and he defended not flattening that: it "can happen when a sender adds a case, but the receiver stills run with an old version of the proto that doesn't have that case" ([comment](https://github.com/scalapb/ScalaPB/issues/633#issuecomment-554368845)). So ScalaPB ships both: the in-family case with a sub-trait by default, and an opt-in `Option` wrapper around the union for oneofs. Neither keeps a payload in the union (it is in `unknownFields`). Outcome (a) for the default, (b) for the opt-in style.
  - An earlier user objection to the wrapper, from olafurpg (Scalameta), in closed [PR #526](https://github.com/scalapb/ScalaPB/pull/526#issuecomment-451641836): "the `Empty` sealed oneof case has worked out great in our experience from Scalameta. Using `Option[SealedOneof]` would be a regression since it makes both construction and pattern matching more complicated, even for simple cases", with the example `Add(Lit(1), Lit(2))` becoming `Add(Some(Lit(1)), Some(Lit(2)))`. He would "prefer exceptions over `Option` if I had to choose" (verified).
  - For enums, no `Option`- or `Either`-typed field was found proposed. The nearest is [#882](https://github.com/scalapb/ScalaPB/issues/882), where a user asked how to avoid handling `Unrecognized` in every match and the maintainer pointed to `myEnum.asRecognized.get match {…}` (verified).

- **Open enums ([PR #1137](https://github.com/disneystreaming/smithy4s/pull/1137), 2023): in-family case, no wrapper discussed.** The description: "open enumerations that are codegenerated with an extra `Unknown` case", needed because "AWS treats enums as open in several places… This PR will allow for maintaining the default of closed enumerations". **smithy-kotlin.**

**smithy-go / AWS SDK for Go v2: why Go keeps tag and bytes.**

- **Stated reason: re-serialization.** The first union generator, commit [8f16276](https://github.com/aws/smithy-go/commit/8f1627616e8ea437c9008dd0729e9e7aa580a575) "Store and expose unknown union tags" (2020), generated a per-union `<Union>Unknown { tag string; value []byte }` with the comments "Creates a fallback type for use when an unknown member is found. **Apollo iOS.**

- **2019 rewrite RFC: unions as an in-enum `__unknown(String)` case, payload-carrying cases rejected for code size.** In [RFC #939](https://github.com/apollographql/apollo-ios/issues/939) (Dec 2019, designatednerd, then maintainer) "Union types will be represented by `String`-backed enums", sketched as `enum CharacterType { case Human; case Droid; case __unknown(String) }`. A user asked for associated values (`case Human(HumanHero)`, `case __unknown(String)`) so that `switch` works. The reply: "Unfortunately that won't work super-well with this setup, since those associated types will be different per query, and I want that union type to work with all queries. Otherwise we'd have to regenerate the union type for everything, and that would be a *ton* of extra code compared to the `as blah` version, especially for APIs that have huge union types" ([comment](https://github.com/apollographql/apollo-ios/issues/939#issuecomment-564112847)). A second proposal for an enum-shaped abstract type got "I'll take a look at this suggestion" ([comment](https://github.com/apollographql/apollo-ios/issues/939#issuecomment-572271530)). Verified. This rejects a *payload-carrying sum type* for unions, for GraphQL-specific reasons (each query selects different fields), not a wrapper.
- **2021 1.0 RFC: a generic `Union<UnionType>` wrapper was proposed, and did not ship.** The 1.0 proposal, in its first version ([CodegenProposal.md at 070ea51, L436](https://github.com/apollographql/apollo-ios/blob/070ea5134f60f5c2a7b78c72c294d993e6304c8e/CodegenProposal.md#L436)) and still in the copy shipped with 1.0 ([at fea2613, L436](https://github.com/apollographql/apollo-ios/blob/fea2613e7d69dbf532b5aad897722be638f345be/CodegenProposal.md#L436)), says: "`UnionType` enums are referenced as fields by being wrapped in a `Union<UnionType>` enum that provides access to the underlying `UnionType` and unknown cases. See Handling Unknown Types". This is the same idea as `OpenUnion[T]`, placed next to the enum wrapper `GraphQLEnum<T>` ([L474-L529](https://github.com/apollographql/apollo-ios/blob/fea2613e7d69dbf532b5aad897722be638f345be/CodegenProposal.md#L474-L529)), so the RFC planned two generic wrappers (verified). What shipped is different: `ApolloAPI.Union` is a metadata struct (`name`, `possibleTypes`), not a wrapper ([Union.swift](https://github.com/apollographql/apollo-ios/blob/fea2613e7d69dbf532b5aad897722be638f345be/Sources/ApolloAPI/SchemaTypes/Union.swift)), and union fields are read through `__typename` and optional `asX` accessors (section 4.2). **No record was found of why `Union<UnionType>` was dropped.** The RFC PR [#1876](https://github.com/apollographql/apollo-ios/pull/1876) review does not discuss it; the repository's pre-1.0 history is squashed into one commit ("release: Apollo iOS 1.0 (#2540)"), and commit search for `UnionType` returns nothing. Outcome (b), proposed and then not implemented, reason unknown.
- **A later request for an enum-with-unknown for unions was welcomed but deferred, for code size.** [#3263](https://github.com/apollographql/apollo-ios/issues/3263) (2023) asked for `switch person { case .student(…); case .employee(…); case .unknown(typeName) }`. AnthonyMDev (maintainer): "This is something we've considered in the past… I'm definitely not opposed to adding this feature. Generating this for every field that references a union may not always been helpful and could significantly increase generated code size. So I think I'd probably want to make it an opt-in feature" ([comment](https://github.com/apollographql/apollo-ios/issues/3263#issuecomment-1780077712)). Still open (verified).
- **The maintainer's stated reason for the enum wrapper is a Swift limitation.** In [#3584](https://github.com/apollographql/apollo-ios/issues/3584) AnthonyMDev: "I have been considering making a change where we deprecate `GraphQLEnum` and instead just generate an unknown case on each of the generated enums. But that would prevent the generated enums from having a `RawValue` and automatic synthesis of `Equatable` and `Hashable` conformance. `@nonexhaustive` resolves this for us completely", and "you're right that we would be able to remove `GraphQLEnum` (and the associated headaches)" ([comment](https://github.com/apollographql/apollo-ios/issues/3584#issuecomment-3286408990)). Verified. So the wrapper was chosen because a Swift enum with an associated-value case loses `RawRepresentable` and synthesized conformances; the maintainer would rather have the in-type case (or a language feature) and calls the wrapper a source of "headaches". The 2019 pre-1.0 design had used exactly the in-enum `__unknown(String)` case.
- **#2678 maintainer reply.** On the `.case(.x)` complaint (section 6), AnthonyMDev: "Yeah, we are aware of this limitation. I know it's not ideal, but Swift can't deduce switch exhaustivity with the pattern matching operator. We provide it as a convenience", recommending a nested `switch` on `.case`/`.unknown` or a `switch` on `.value` with `.none` ([comment](https://github.com/apollographql/apollo-ios/issues/2678#issuecomment-1371408617)). No defence of the wrapper as such (verified).

**Apollo Kotlin.**

- **A user asked for the iOS wrapper's ergonomics; the maintainers answered with a sub-interface, not a wrapper.** In [#6243](https://github.com/apollographql/apollo-kotlin/issues/6243) (2024) a user who uses both clients wrote that Apollo iOS's `GraphQLEnum<T>` "is instead a wrapper enum around the core enum. On first glance, you would think Kotlin's approach is nicer because you don't need to match `.case(...)`, but every single when statement needs a default case to handle the `.UNKNOWN__`, whereas iOS I can just create an unwrapper at the top level of my project to handle `.unknown` once", and that "Apollo iOS wins for the power use cases" ([comment](https://github.com/apollographql/apollo-kotlin/issues/6243#issuecomment-2460983328)). martinbonnin (maintainer) implemented an intermediate `KNOWN__` sealed interface "symmetrical with `UNKNOWN__`", which "allows unwrapping an unknown value to a known one" ([PR #6248](https://github.com/apollographql/apollo-kotlin/pull/6248)). A wrapper type was not discussed as an option; the sub-interface gives the same "unwrap once" property inside the family (verified; inference that this is the reason a wrapper was not needed).
- **A maintainer reservation about handling unknowns generically.** When a user asked for common generic interfaces so that one `knownOrElse` works for all enums, martinbonnin replied: "I'm not sure handling `UNKNOWN__` globally is a pattern that we want to encourage. The consumer of the enum needs to make a choice about how to handle the unknow enum. That choice depends on the use case… I like that the exhaustive `when` forces to be aware of this choice", and "the prospect of modelling this better in the type system is appealing but we'd probably need more feedback before commiting to a certain direction" ([comment](https://github.com/apollographql/apollo-kotlin/issues/6243#issuecomment-3028817793)). He nevertheless shipped the generic interfaces `ApolloEnum<E, K : KnownEnum<E>>` with a `__Known` sub-interface behind a new flag, `generateApolloEnums` ([comment](https://github.com/apollographql/apollo-kotlin/issues/6243#issuecomment-3036493432), [PR #6611](https://github.com/apollographql/apollo-kotlin/pull/6611)), noting "I'm not thrilled by the accumulation of flags". Verified. This is the only maintainer statement found that argues *against* the main benefit Telegramium wants from a generic mechanism (handling unknowns once, generically), though it was not about a wrapper and he shipped the feature anyway.
- **Sealed classes versus Kotlin enums: decided on interop and convenience, not on wrapper versus case.** [#3501](https://github.com/apollographql/apollo-kotlin/issues/3501) (2021) moved the default back from sealed classes (which keep the raw value) to Kotlin enums with a lossy `UNKNOWN__` constant: "As most users would probably expect generating enums, and not often need the `rawValue` provided by sealed classes, let's go back to default to enum generation" ([comment](https://github.com/apollographql/apollo-kotlin/issues/3501#issuecomment-968756132)), after testing how both look from Swift via Kotlin Multiplatform (verified).
- **Private `UNKNOWN__` construction (4.0).** [#5796](https://github.com/apollographql/apollo-kotlin/issues/5796): a user could pass `SomeEnum.UNKNOWN__` as mutation input, which "will always fail on the backend validation". The fix went from an `@OptIn` annotation ([#5813](https://github.com/apollographql/apollo-kotlin/pull/5813)) to removing the constructor: "in #5904 we ended up removing the `@OptIn` annotation, and instead removed the UNKNOWN__ constructor. Now `safeValueOf` should be used" ([comment](https://github.com/apollographql/apollo-kotlin/issues/5796#issuecomment-2136842825)). Verified. No wrapper discussed.

**FIDL (Fuchsia IDL): the most detailed design record found, and it went the other way.** Not in the task list; found through the code search below. FIDL has "flexible" enums and unions with an unknown state in every binding, and two RFCs set the rules. Links are pinned to fuchsia commit `4735d6a`.

- **[RFC-0033](https://fuchsia.googlesource.com/fuchsia/+/4735d6a64a8c5b706a43e49b335f761b6db5cad4/docs/contribute/governance/rfcs/0033_handling_unknown_fields_strictness.md) (2019): an in-type unknown tag, for exhaustiveness.** "If the target language offers a mechanism to exhaustively check tags at compile time… That language binding SHOULD offer a special 'unknown' tag that can be included as part of the exhaustive check, so that a catch-all case… can be omitted… because if it is, tags added in the future will not elicit compiler warnings." Bindings "MAY provide a mechanism to read the tag, raw data, and (untyped) handles in an unknown field". The RFC's listed alternatives are about strict versus flexible defaults and keywords, not about representation; a wrapper is not mentioned (verified).
- **[RFC-0137](https://fuchsia.googlesource.com/fuchsia/+/4735d6a64a8c5b706a43e49b335f761b6db5cad4/docs/contribute/governance/rfcs/0137_discard_unknown_data_in_fidl.md) "Discard unknown data in FIDL" (2021): payloads of unknown union variants were deliberately dropped.** After about a year of most bindings keeping unknown union bytes and re-encoding them, the RFC changed the rule so that for unions "Can access unknowns? Yes → Ordinal only; Can re-encode? Yes → No", while enums keep their unknown integer. Reasons given:
  - "Proxying is the only realistic use case for preserving unknown data", and the feature "has seen little or no use in Fuchsia, and it has repeatedly come up as a complicating factor in other FIDL efforts".
  - Proxying only works on direct re-encoding, but "it is common (and recommended) to convert these objects to richer, application-specific types before further processing", so multi-hop systems cannot rely on it anyway.
  - It makes wire-format migrations hard, cannot be implemented in in-place-decoding bindings, and interacts badly with other features; it also carries "security and privacy risks" (from the summary).
  - The RFC names the cost: "it makes the behavior of flexible types less consistent… going from `Enum` to `Union`… that functionality comes with the cost of no longer preserving unknowns", and accepts "this trade-off of pragamatism over consistency".
  - Equality: unknown union variants "should behave like NaN… comparing unequal even if ordinals are the same", so Rust flexible unions lose `Eq`.
- **An `Option`-style alternative was considered and not chosen.** "Alternative: Optional flexible unions: … we could require that flexible unions are always optional, and then decode unknown variants as absent unions. This would make it possible to re-encode unions, making them consistent with tables." The RFC lists it without a separate rebuttal; the design section keeps the in-union unknown state with the ordinal (verified). "Alternative: Optionally preserve unknowns" (opt-in payload keeping) was rejected because it "adds even more complexity to a little-used feature, and it does not solve the wire format migration problem".
- **Generic `MaybeUnknown<T>` exists in FIDL's Rust runtime, but not for data.** `fidl_message` has `pub enum MaybeUnknown<T> { Known(T), Unknown }`, the "Return type for functions that decode flexible responses", where `Unknown` means "The server did not recognize the method ordinal" ([lib.rs L109-L115](https://github.com/artem/fuchsia-mirror/blob/HEAD/src/lib/fidl/rust/fidl_message/src/lib.rs#L109-L115), read in a GitHub mirror, not pinned). So FIDL uses a generic wrapper around a result and an in-type unknown state inside unions, side by side. Outcome: (a) for keeping union payloads (rejected, with reasons), an `Option` wrapper listed as an alternative without stated rejection.
- Relevance to Telegramium (inference): FIDL's reasons are specific to a binary IPC system with handles and in-place decoding. Its one general argument, that proxying unknown data rarely survives conversion to application types, applies to a bot library only where a bot forwards objects it received; a Telegram bot does send received `MessageEntity` lists back (copying or editing messages), which is the case `raw` serves.

I would love a PR to implement it!" ([comment](https://github.com/serde-rs/serde/issues/912#issuecomment-300359258)) for `#[serde(other)]` on internally tagged enums. An early participant suggested data-less only: "I would assume the most sensible thing would be to only allow this annotation on data-less variants… I don't think it'd be wise to try to deserialize the unknown tag's data into some other variant's data." dtolnay posts nothing on representation in [#1701](https://github.com/serde-rs/serde/issues/1701) or [#1973](https://github.com/serde-rs/serde/issues/1973) (verified: author lists checked).
